# Lab 2 Sprint Engineering Specification — TokTickIT Requester MVP

## 1. Sprint Goal
Deliver a working Requester-facing ticketing experience: a Requester (selected via a temporary
Development Requester selector) can create an IT support ticket with attachments, browse and
search their own tickets, open a Ticket Detail screen, and manage their own attachments — all
built on a real PostgreSQL/Prisma backend and a responsive Zen Green UI, with ownership strictly
enforced so no Requester can see another Requester's data.

## 2. Stakeholder Request Interpretation
IT is ready for real requests. We need a professional, responsive self-service ticket flow
(create → confirm number → track in My Tickets → inspect in Ticket Detail → manage attachments),
without building real authentication yet. A temporary "Development Requester Selection" screen
stands in for login so multi-user ownership can be tested. All screens follow one reusable visual
language (Zen Green) so later sprints don't reinvent styling.

## 3. Scope
### Included
- Development Requester Selection (testing-only identity switch)
- Create Ticket (form, validation, attachment upload, Ticket Number generation)
- My Tickets (search, filter, sort, pagination, empty/no-results states)
- Requester Ticket Detail (read-only ticket info + attachments)
- Attachment lifecycle: upload, list, download, soft-remove
- Ownership enforcement on every ticket/attachment read and write
- Zen Green reusable UI components (form, list, badge, states)

### Excluded
- Real authentication (passwords, sessions, tokens, RBAC)
- IT Staff dashboard, claiming, IT Priority changes
- Public Comments, Internal Notes, Actions Taken
- Ticket status transitions beyond initial `New`
- Administration of users/reference data

## 4. Functional Requirements
- FR-01 The system shall let the user pick one active Development Requester before any ticket
  screen is usable, and shall persist that selection as the current session context.
- FR-02 The system shall let the user change the active Development Requester at any time via a
  "Change Requester" action, reloading all requester-scoped data.
- FR-03 The system shall allow the current Requester to create a ticket by submitting Category,
  Related System, Summary, Requested Priority, Description, and 0–5 attachments.
- FR-04 The backend shall generate a unique, sequential Ticket Number (format `TKT-YYYY-NNNNNN`)
  on successful creation; the client shall never submit a Ticket Number.
  For example, the first ticket created in 2026 receives `TKT-2026-000001`.
- FR-05 The system shall set `currentStatus = NEW` and `ticketDate = now()` automatically on
  creation.
- FR-06 The system shall list only tickets owned by the current Requester in My Tickets.
- FR-07 The system shall support searching My Tickets by Ticket Number or Summary (case-insensitive,
  partial match).
- FR-08 The system shall support filtering My Tickets by Category, Requested Priority, IT Priority,
  and Current Status.
- FR-09 The system shall support sorting My Tickets by Created Date, Last Updated, Requested
  Priority, and Ticket Number, ascending or descending.
- FR-10 The system shall paginate My Tickets results with a default page size of 10 and a maximum
  of 50.
- FR-11 The system shall allow the current Requester to open Ticket Detail only for tickets they own;
  any other ticket access shall return a 404-style "not found" response (never a 403 that reveals
  existence).
- FR-12 The system shall allow the current Requester to add an attachment to their own ticket if it
  has fewer than 5 active attachments.
- FR-13 The system shall allow the current Requester to soft-remove one of their own active
  attachments by providing a removal reason.
- FR-14 The system shall prevent download or preview of a soft-removed attachment while still
  showing its metadata (filename, size, removed date, remover) in the UI.
- FR-15 The system shall show clear loading, empty, no-results, validation, and failure states on
  every screen described above.

## 5. Business Rules
- BR-01 The official Ticket Number is generated by the backend and must be globally unique.
- BR-02 A new Ticket always begins with `currentStatus = NEW`.
- BR-03 The Development Requester selector is a Lab 2 testing mechanism only; it performs no
  password check, issues no session token, and must not be described to the user as a login.
- BR-04 Only Requesters with `isActive = true` appear in the Development Requester selector.
- BR-05 If an inactive Requester is somehow selected (e.g., stale client state), any subsequent
  ticket/attachment request on their behalf is rejected with a safe error and the user is returned
  to the selection screen.
- BR-06 A Ticket may only be read, updated, or have attachments modified by the Requester who owns
  it; ownership is enforced server-side on every request, never trusted from the client alone.
- BR-07 Ticket Summary is required, trimmed, 5–120 characters.
- BR-08 Ticket Description is required, trimmed, 10–2000 characters.
- BR-09 Category and Related System must reference existing, active reference records; an unknown
  or inactive id is rejected with 400.
- BR-10 Requested Priority must be one of `LOW`, `MEDIUM`, `HIGH`.
- BR-11 Duplicate-submission prevention: the Submit button is disabled and shows a busy state while
  a create-ticket request is in flight; a second click before the first response returns is ignored
  client-side, and the server treats each request independently (no idempotency key required for
  Lab 2, but the UI must not allow accidental double submission).
- BR-12 If ticket creation fails after the ticket row is written but before all attachments upload,
  the ticket is still considered created (its number is valid); the UI reports which attachments
  failed and lets the Requester retry adding just those files from Ticket Detail.
- BR-13 Allowed attachment types: JPG, JPEG, PNG, WEBP, PDF. Maximum size: 5 MB per file. Maximum 5
  active attachments per ticket.
- BR-14 An attachment exceeding the size/type/count limit is rejected before upload starts, with a
  field-level message; no partial file is stored.
- BR-15 Attachment removal is soft: `isRemoved`, `removedAt`, `removedBy`, `removalReason` are set;
  the file remains in storage for audit but is never served to any download/preview endpoint once
  removed.
- BR-16 Removal requires a non-empty removal reason (min 5 characters) and a confirmation step in
  the UI before the request is sent.
- BR-17 Only the owning Requester may remove their own attachment; there is no removal of another
  Requester's attachment in Lab 2 (no IT Staff role exists yet).
- BR-18 My Tickets returns an "empty state" (no tickets ever created) distinctly from a "no results"
  state (filters/search matched nothing).
- BR-19 Search, filter, and sort parameters are validated; unknown/invalid values fall back to
  defaults rather than erroring, so a bad query string never breaks the list.
- BR-20 In Lab 3, the Development Requester selector will be replaced by real authentication; the
  `requesterId` used throughout Lab 2's API will map to the authenticated user's id, so no schema
  rename should be required — only the source of truth for identity changes.

## 6. UI Specification Summary
See `ui-spec.md` for full detail. Summary: app shell (TokTickIT header, My Tickets / Create Ticket
nav, current Requester + Change Requester), Zen Green tokens (primary #006B3C, secondary #0B7A46,
pale #EAF6EF, background #F5F7F6), consistent field/badge/button states (editable, read-only, error,
disabled, busy), and three responsive breakpoints (desktop ≥992px, tablet 768–991px, mobile <768px).

## 7. Data Changes
Prisma models (see `api-spec.md` for full field list):
- `Requester` (id, name, email, isActive, timestamps)
- `Category` (id, name, isActive)
- `RelatedSystem` (id, name, isActive)
- `Ticket` (id, ticketNumber [unique], requesterId [FK], categoryId [FK], relatedSystemId [FK],
  summary, description, requestedPriority, itPriority [nullable, Lab 3+], currentStatus,
  ticketDate, createdAt, updatedAt)
- `Attachment` (id, ticketId [FK], fileName, storedFileName, mimeType, sizeBytes, uploadedAt,
  isRemoved, removedAt, removedBy, removalReason)

Indexes: unique on `ticketNumber`, `Requester.email`; composite index on
`(requesterId, createdAt)` for My Tickets queries; index on `Attachment.ticketId`.

## 8. API Contract
Full contract in `api-spec.md`. Endpoints: `GET /api/categories`, `GET /api/related-systems`,
`GET /api/requesters`, `POST /api/tickets`, `GET /api/tickets`, `GET /api/tickets/:id`,
`POST /api/tickets/:id/attachments`, `GET /api/attachments/:id`,
`GET /api/attachments/:id/download`, `POST /api/attachments/:id/remove`.

## 9. Acceptance Criteria
- AC-01 Given valid ticket data, when the Requester submits the form, then one Ticket is saved and
  the official Ticket Number is displayed.
- AC-02 Given no Development Requester is selected, when the user attempts to open My Tickets, then
  the Requester Selection screen is shown.
- AC-03 Given Requester B is selected, when a Ticket belonging to Requester A is requested, then the
  Ticket data is not returned.
- AC-04 Given Summary is blank, when the Requester submits, then a field-level error is shown and no
  API call is made.
- AC-05 Given a slow/failing network, when the Requester submits, then form values are preserved and
  a safe error message is shown.
- AC-06 Given a 6 MB file, when the Requester attaches it, then it is rejected before upload with a
  size error.
- AC-07 Given 5 active attachments already exist, when a 6th is attempted, then it is rejected with a
  count error.
- AC-08 Given a Requester has zero tickets, when My Tickets loads, then the empty state (not the
  no-results state) is shown.
- AC-09 Given a search term matches no ticket, when My Tickets loads, then the no-results state is
  shown with a "clear filters" action.
- AC-10 Given 42 tickets and page size 10, when the Requester opens page 3, then tickets 21–30 are
  shown with correct pagination controls.
- AC-11 Given an active attachment, when the Requester downloads it, then the original file is
  returned.
- AC-12 Given a removed attachment, when the Requester attempts to download it, then the request is
  rejected and the UI shows it as unavailable while keeping its metadata visible.
- AC-13 Given the Requester provides a removal reason and confirms, when they remove an attachment,
  then it becomes soft-removed and disappears from the active list but remains in the removed list.
- AC-14 Given the viewport is <768px, when any Lab 2 screen is viewed, then fields stack vertically
  with no horizontal scrolling.
- AC-15 Given the Requester switches from A to B via Change Requester, when My Tickets reloads, then
  only B's tickets are shown.
- AC-16 Given an inactive Requester exists, when the Development Requester dropdown loads, then that
  Requester does not appear.
- AC-17 Given the reference-data API fails, when Create Ticket loads, then a safe failure state is
  shown instead of a blank or crashed form.

## 10. Definition of Done
- All FR/BR/AC above implemented and traceable to passing tests in `tests.md`.
- No test skipped, disabled, or commented out in the final `main` branch.
- Ownership enforced server-side for every ticket/attachment endpoint (verified by tests).
- Zen Green tokens and component states match `ui-spec.md`; verified with Playwright screenshots at
  desktop/tablet/mobile.
- Seed data runs idempotently (no duplicates on repeat `prisma db seed`).
- README documents setup, seed, and test commands and is current.
- Peer-reviewed PRs merged through `lab2-staging` → `main`; `reviewer.md` completed.

## 11. Assumptions and Decisions
- Ticket Number format chosen as `TKT-YYYY-NNNNNN` (sequential per year) for readability and
  collision-safety; enforced via a DB unique constraint plus a serial/sequence, not just app logic.
- Ownership failures return 404 rather than 403 to avoid confirming a ticket's existence to a
  non-owner (information-disclosure minimization), matching FR-11.
- IT Priority field exists in the schema now (nullable) so Lab 3's IT Staff workflow doesn't require
  a migration, but it is never set or shown as editable in Lab 2.
- Default page size 10, max 50, to keep My Tickets responsive on mobile.
